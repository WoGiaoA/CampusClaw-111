# Design

## Context

见 proposal.md 的动机。现有 `Server.Handler` 没有 DELETE 材料路由；材料行由共用前端渲染器生成，教师和学生均有查看/下载。MySQL `materials` 被全文、索引任务、切片及 `assistant_materials` 外键依赖。索引器周期补齐缺失任务，随后调用 Embedding/Qdrant；仅在末尾检查批次状态，尚不能阻止删除后迟到的向量写入。Qdrant 候选会回表核对，但当前没有删除状态过滤。

第5课历史引用以JSON保存在消息元数据中，回放发现材料不存在时清空引用信息，前端仅显示“来源当前不可用”；这不足以区分明确删除和存续材料重建。启动时 Reconcile 假设每份材料都有全文和文件；增加删除状态后必须同时调整，否则已删文件会导致启动失败。

## Goals / Non-Goals

Goals：以MySQL持久化撤回作为业务生效点；跨存储最终清理可恢复；单实例部署中明确解决索引迟到写入；教师可取消、可核对操作状态。

Non-Goals：不做回收站、恢复、批量删除或物理删除历史会话；不保证撤回已经发给外部模型的内容；不启停主容器，不修改现有密码和真实材料；不提前归档其他change。

## Decisions

### 1. 持久化撤回与最终清理分离

增量迁移为材料增加删除时间，新增以material_id唯一的清理记录，至少保留class_id、可信storage_key、清理状态、有限错误码和重试时间。保留材料最小墓碑行用于外键稳定和班级内410判断；清理完成后不保留全文或文件内容，材料ID不复用。删除操作在短事务内锁定本班材料、设置删除标记、移除全部应用绑定并持久化清理任务；提交失败不进行外部删除。

不采用“先删文件再删数据库”，因为事务失败会造成仍可见材料丢失原文；不采用“所有外部调用包在长事务里”，因为Qdrant与文件系统无法参与MySQL原子提交且会长期持锁。业务撤回不可逆，后台保留任务不表示可恢复或回收站。

### 2. API与重复请求

新增DELETE /api/materials/{id}，沿用Bearer/Cookie、首次改密和CSRF。先检验教师/CSRF，再按可信班级查材料。正常不存在/跨班404；本班已删除记录返回已有清理状态。首次持久化受理通常返回202 `{material_id,status:"cleanup_pending"}`；清理已完成返回200 `{material_id,status:"deleted"}`。JSON错误沿用error并提供稳定code，内部路径、外部响应原文不得回传。

现有本班GET材料/文件/切片/对应知识库详情及重建遇删除墓碑返回410和material_deleted；外班始终404。响应先查材料及可信班级，再查正文，避免因全文已清除而无法识别删除状态。不存在的普通ID仍404。无需新增管理面板：教师可刷新列表，重复同一DELETE安全返回当前状态；待清理记录由后台自动推进，错误详情不泄露凭据。

### 3. 所有入口以当前删除状态为准

材料和知识库列表排除墓碑；`hitJoin`及向量签名检查排除删除材料，不能让已删任务引起无关的模型签名错误。向量查询返回的ID继续按同班、存续材料、有效代次和ready回表，永远不从Qdrant读取正文。应用绑定读写和每轮快照均验证存续状态。删除事务同步删绑定，绑定写事务与删除共享材料行的锁定顺序，防止检查通过后又插回绑定。

`enqueueMissing`仅为存续材料登记；重建及索引选取、发布ready再次检查存续状态。旧`/materials`、工作台列表、知识库详情和检索/MCP knowledge_search均沿用同一过滤规则，不只修改一个页面。删除导致应用没有资料时使用原有unbound语义，不能将空集合理解为全班。

### 4. 索引协调与清理顺序

沿用项目明确的单API实例边界，引入按material_id的生命周期协调器，覆盖索引构建的完整外部写入阶段与删除清理。它负责串行化同材料索引写入和最终向量清理，并允许撤回提交后通知活动索引取消。索引取消需等待调用返回，不得只因context已取消就认定上游未写入。即使通知失效，删除标记也阻止后续批次与ready发布。

清理器仅在取得同材料生命周期锁并确认本进程无该材料活动写入后执行。必须验证Qdrant对删除后迟到写入的处理：客户端取消或超时不能被当作远端已停止执行的保证。对未确定的写入保留任务，进行最终重复过滤删除及确认；未能确认时继续pending，不宣称清理完成。重启后先恢复删除任务，阻止墓碑补索引，再执行幂等收尾。

清理按可信class_id与material_id过滤Qdrant points/delete?wait=true，仅删除该材料向量；目标集合不存在可视为已无向量，其余外部故障留待重试。持有生命周期协调期间在短MySQL事务内按外键顺序删除切片、索引任务、全文，保留墓碑与任务；通过storagePath校验原文件属于上传根目录，再删除原文件，缺失视为已完成；所有部分完成均可重入。最后核对无残留并标记完成。文件删除失败或Qdrant不可达不得影响已经提交的业务撤回，也不得误改其他材料。

启动Reconcile对存续材料保持原有完整性验证，对删除记录允许全文/文件已清理；待清理文件仍按可信任务记录管理。不因墓碑启动失败、不通过补种子或自动补索引复活已删除材料。清理重试使用有界退避，单任务故障不能阻塞全部资料或登录。

### 5. 历史与生成中的引用

扩展引用响应为可选source_status（available/material_deleted/source_unavailable）。保持历史正文与编号；针对本人同班会话，已删除引用响应仅保留安全编号和失效状态，清空片段、摘录、URL及字符位置等附件；不将墓碑标题或状态泄露给跨班请求。前端优先判断source_status，显示明确已删除提示且无链接/展开片段。

存续材料重建后沿用原文回退，不能标成material_deleted。当前页面旧链接请求遇410时更新来源反馈；通用404仍用不可用提示。历史正文可能已经包含旧资料摘录，删除不自动重写历史回答，也不保证模型忘记已发送上下文，此边界写入操作说明。

删除提交后开始的请求不读该材料。已在生成中的请求可能已经用过其片段；保存/回放及最终done引用执行当前状态复核，不把已删除片段作为可用附件输出。无法追溯撤销已传输给客户端的字节，不承诺实时清空其他已打开页面，但后续访问/刷新必须正确失效。

### 6. UI兼容与确认

共用材料列表中仅教师有删除按钮，沿用现有SVG、黑色图标和文字操作样式（查看、下载、删除之间各有浅灰竖线）和对话框。弹窗包括文件名和影响，默认焦点放取消，Escape关闭并恢复焦点。确认期间禁用重复提交。202提示“材料已停止使用，关联资源正在清理”，200提示“材料已删除”；受理后删除对应行、更新数量，并从服务端重读列表。刷新失败不能改报删除失败。未受理失败保持原行可用并显示可读错误。现有查看下载行为不改变。

## Risks / Trade-offs

- [跨存储没有原子提交] → 立即撤回与持久化幂等清理解耦，只有全部确认才置完成。
- [索引或Qdrant请求迟到写入] → 生命周期串行化、取消后等待、删除标记检查、最终过滤删除及不确定状态保留重试；必须有延迟上游的故障测试。
- [清理后启动对账错误] → 同步更新Reconcile、种子及补索引条件，验证删除后两次启动不复活。
- [历史回答仍有旧信息] → 明确保留正文、撤销来源附件的边界；不宣称删除会话历史或远端模型数据。
- [软删除被误当作只隐藏列表] → 最终清除全文、切片、任务、原文件、向量和绑定；只留最小墓碑，测试逐存储核对。

## Migration Plan

1. 增量迁移默认全部存续，重复执行安全，不重新向量化。先在空隔离库和已有第5/6课数据夹具上验证。
2. 完成API、过滤、生命周期协调、恢复、引用与UI后，执行隔离MySQL/Qdrant和Mock模型验证；不读取课程网关密钥或消耗真实额度。
3. 留存脱敏测试结果与Windows CMD启动说明，由用户备份数据库/原文件后更新部署并人工验收。
4. 删除不可撤销；若需回滚应用，不得直接退回忽略删除标记的旧版本，否则会复活墓碑。保留兼容过滤修复或停止使用该功能后部署修复版本，恢复备份须成套处理数据库、原文件及索引。
